# 119警情WGS84转换及大厂范围过滤

## 启用步骤

1. 在现有 `dachang` 数据库执行 `SQL/fire_119_gcj02_scope_upgrade.sql`。可重复执行，新增几何状态、规则版本、距边界米数及索引；不删除警情、不修改人工归属，不调用外部接口。
2. 在IDE运行最新 `ruoyi-admin`（或重新打包部署后端），前端开发环境刷新，部署环境使用最新构建。
3. 配置已设置为 `fire.incident119.source-coordinate-system: WGS84`、`boundary-coordinate-mode: verified`、`dachang-only: true`。这些设置只作用于119，不转换已有场所、摄像头或传输装置坐标。
4. 启动后按现有延迟进入同步。后台先分批重算历史原始数据，再请求上游。无需人工打开网页，也不需要高德Key参与运行。

本次仅在隔离数据库验证，没有修改业务数据库或启动实际119采集。请先执行升级SQL再启动新版本，否则新字段查询会失败。

## 判断规则

流程：源WGS84 → 本地GCJ-02 → 用户33点闭合多边形 → 统一展示过滤。采用的本地公式已经过225点官方JS转换对照（平均差异约5.6厘米、最大约11.4厘米，属于该批样本结果而非全球上限）。原始坐标及raw_json保留；地图使用单独map_longitude/map_latitude，前端不再转换。

当前边界为用户2026-10-28提供的33点，文件 `ruoyi-system/src/main/resources/fire/dachang-119-scope.json`，不是旧文档25区域的并集。边线及顶点计入；范围外、缺失、非法或待核验数据仍入库但不进入大厂119列表。保留全部案件类型和源平台状态。人工归属信息保留，但不能覆盖几何范围过滤。旧版本几何结果不能用于新范围展示。

查询列表、详情、地图使用相同服务端范围及若依数据权限。统计中的inside/outside/pending使用相同版本；版本尚未重算的记录计入pending。不存在通过传入dachangOnly=false、旧版本或直接访问详情来绕过范围的方法。

距边界约1米以内的可见警情，详情增加“建议人工核验”提示。距离采用大厂附近局部米制近似，仅用于提示，不将框外点自动纳入。

## 历史重算和检查

重算从数据库保存的原始raw_json读取，不依赖上游仍返回该条记录。每批最多200条、独立事务；完整同步每轮最多20批，快速同步最多一批，受现有同步总时限和停止信号约束。较大存量会在后续轮次继续。异常源数据标为待核验；数据库异常则事务回滚并进入现有重试机制。

只更新派生坐标、坐标系标识和范围结果；保留原始来警时间、首次接收/最近接收/原始变更时间和事件历史，不产生“新警情”提醒。日志可查“119历史坐标重算”。重算期间旧版记录暂不显示，后续逐步恢复范围内数据。

可在导入后自行检查（只读）：

```sql
SELECT source_coord_system, geofence_version, geofence_status, COUNT(*) AS row_count
FROM dachang.fire_119_incident
WHERE source_system='jiangning_119'
GROUP BY source_coord_system, geofence_version, geofence_status;
```

当前业务数据库内条数没有在本次工作中查询，实际范围内/范围外/待判定数量以部署重算后的统计为准。大屏底图原有社区名称/分区图层保持原样，不作为本次119的过滤依据。

## 2026-10-29 用户调整：增加“大厂”关键词

最新展示规则为：当前版本坐标在33点范围内，**或者**案发地址（afdz/address）、警情描述（ajms/description）任一包含“大厂”。按字面匹配，不做地址语义推断。框外、无效/缺失坐标和旧坐标版本的记录，只要含关键词也纳入；已有历史记录立即适用，无须重新拉取。两条规则同时命中只显示一条。

本次不修改坐标/几何归属，也不新增表字段；列表、详情、地图数据源及统计共用规则，部门/人员权限继续生效。没有有效坐标的关键词记录显示在列表中，不虚构地图位置。insideCount/visibleCount表示合并纳入数量；keywordCount表示关键词命中数量（可与坐标命中重叠），outside/pending只计未被上述规则纳入的记录。

已执行上一版坐标升级SQL的环境，仅需重启更新后的后端并更新前端，无须新增SQL。本文此前“只按几何范围”等排除性规则以本节为准。
